# G6.2 Araç ve Şoför Ataması: PostgreSQL Concurrency ve Row-Lock SQL İncelemesi

**Tarih:** 2026-08-16
**Durum:** Kodlama öncesi SQL/concurrency design review
**Bağımlılık:** `g6.2-vehicle-driver-routing-design.md`
**Kapsam:** Aynı araç veya şoförün çakışan rotalara eşzamanlı atanmasını engellemek

## 1. Problem tanımı

Araç ve şoför ataması yalnızca `route_plans.vehicle_id` ve `route_plans.driver_id` alanlarını güncellemek değildir. Aynı zaman aralığında iki farklı route planının aynı aracı veya şoförü kullanması, iki HTTP isteği birbirinden habersiz şekilde aynı anda çalıştığında ortaya çıkan bir **write skew/phantom conflict** problemidir.

Basit bir akış güvenli değildir:

```text
Transaction A: araçta çakışan rota var mı? → yok
Transaction B: araçta çakışan rota var mı? → yok
Transaction A: route A’ya aracı yaz
Transaction B: route B’ye aracı yaz
Transaction A/B: ikisi de commit
```

Burada iki işlem aynı mevcut route satırını kilitlemiyor olabilir; çünkü her biri henüz farklı route plan satırına yazmaktadır. Bu nedenle yalnızca `route_plans` satırındaki optimistic `row_version` yeterli değildir. Atama transaction’ı ayrıca **kaynak araç ve şoför satırlarını kilitlemeli**, kilit alındıktan sonra aktif route’ları yeniden okumalı ve uygunluk kontrolünü aynı transaction içinde yapmalıdır. Bu yaklaşım, kabul edilmiş `Read Committed + deterministic SELECT FOR UPDATE + re-read` baseline’ı ile uyumludur [1].

## 2. Concurrency sözleşmesi

### 2.1 Isolation seviyesi

MVP baseline’ı PostgreSQL `READ COMMITTED`’dır. Her SQL statement kendi transaction snapshot’ını görür; `SELECT FOR UPDATE` ile kilitlenen vehicle/driver satırı transaction sonuna kadar korunur. Kilidi bekleyen ikinci command, ilk transaction commit ettikten sonra kendi statement’ını devam ettirdiğinde güncel row ve güncel route overlap sonuçlarını yeniden okumalıdır.

`SERIALIZABLE` bütün command’ler için varsayılan yapılmayacaktır. Serializable veya deadlock retry, idempotent command ve sınırlı retry policy ile ayrıca ele alınabilir. Row lock mekanizmasının çalışması için her resource-assignment writer’ın aynı lock order’ı kullanması zorunludur.

### 2.2 Resource reservation policy

Bu dokümanda route planın araç/şoför atanmış ve zaman aralığı dolu `Draft` state’i **provisional resource reservation** kabul edilir. Böylece kullanıcı araç/şoför seçtiğinde aynı zaman aralığında başka route planı aynı kaynağı alamaz.

| Route state | Zaman aralığı dolu mu? | Resource conflict’e dahil mi? |
|---|---:|---:|
| `Draft`, resourcesiz | Hayır veya eksik | Hayır |
| `Draft`, vehicle/driver atanmış | Evet | Evet |
| `Planned` | Evet | Evet |
| `Locked` | Evet | Evet |
| `InProgress` | Evet | Evet |
| `Completed` | Geçmiş | Hayır |
| `Cancelled/Superseded/Exception` | Policy’ye bağlı | Normalde hayır |

Bu politika terk edilmiş draft’ların kaynakları sonsuza kadar kilitlememesi için `draft_expires_at` veya operasyonel cleanup command’i gerektirir. Alternatif olarak ilk implementation’da `Draft` resource assignment kabul edilmeyip atama yalnızca `Planned` command’inde yapılabilir. Bu iki seçenekten biri implementation gate’inde kesinleştirilmelidir; aşağıdaki sorgular atanmış `Draft`’ı conflict’e dahil eden seçeneği kullanır.

### 2.3 Zaman aralığı semantiği

Route zaman aralığı UTC ve yarı açık interval olarak yorumlanır:

```text
[start_at, end_at)
```

İki interval aşağıdaki koşulla çakışır:

```sql
existing.planned_start_at < :candidate_end_at
AND existing.planned_end_at > :candidate_start_at
```

Bu nedenle `08:00–10:00` ile `10:00–12:00` çakışmaz. `planned_end_at <= planned_start_at` geçersizdir.

## 3. Varsayılan tablo ve constraint önkoşulları

Canonical SQL’de araç, şoför ve route plan tabloları tanımlanmıştır; uygulama migration’ında `row_version`, status check’leri, schedule index’leri ve route version uniqueness açıkça bulunmalıdır [2]. Aşağıdaki örnekler isimleri sadeleştirilmiş mevcut hedef şemayı varsayar.

```sql
-- Örnek varsayımlar; migration yerine design reference'tır.
-- Gerçek migration mevcut naming convention'a göre üretilecektir.

ALTER TABLE vehicles
    ADD COLUMN IF NOT EXISTS row_version bigint NOT NULL DEFAULT 1;

ALTER TABLE drivers
    ADD COLUMN IF NOT EXISTS row_version bigint NOT NULL DEFAULT 1;

ALTER TABLE route_plans
    ADD COLUMN IF NOT EXISTS row_version bigint NOT NULL DEFAULT 1;

ALTER TABLE route_plans
    ADD COLUMN IF NOT EXISTS replanned_from_id uuid
        REFERENCES route_plans(id) ON DELETE RESTRICT;

ALTER TABLE route_plans
    ADD CONSTRAINT route_plans_valid_time
    CHECK (
        planned_start_at IS NULL
        OR planned_end_at IS NULL
        OR planned_end_at > planned_start_at
    );

ALTER TABLE route_plans
    ADD CONSTRAINT route_plans_valid_version
    CHECK (version > 0);

CREATE UNIQUE INDEX IF NOT EXISTS ux_route_plans_shipment_version
    ON route_plans (shipment_id, version);

CREATE INDEX IF NOT EXISTS ix_route_plans_vehicle_schedule
    ON route_plans (vehicle_id, planned_start_at, planned_end_at)
    WHERE vehicle_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS ix_route_plans_driver_schedule
    ON route_plans (driver_id, planned_start_at, planned_end_at)
    WHERE driver_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS ix_vehicles_availability
    ON vehicles (status, maintenance_until);

CREATE INDEX IF NOT EXISTS ix_drivers_availability
    ON drivers (is_active, license_expiry);
```

`row_version` için trigger veya application-side monotonic increment seçilmelidir; iki yöntemin aynı entity’de birlikte source of truth yapılması doğru değildir. Public API değeri ETag olarak sunulur; PostgreSQL `xmin` public contract değildir [1].

## 4. Deterministic row-lock sırası

Tüm assignment ve route-lock command’leri aşağıdaki sabit sırayı kullanmalıdır:

```text
1. RoutePlan
2. Shipment
3. Vehicle
4. Driver
5. RoutePlan’ın mevcut active kaynak kayıtları
6. State/version update
```

Aynı transaction içinde birden fazla route veya resource kilitlenecek gelecekteki command’ler de tablo ve ID sırasını korumalıdır. “Önce route’a göre”, “önce araca göre” gibi iki farklı writer lock order kullanırsa deadlock riski oluşur.

### 4.1 RoutePlan ve parent Shipment lock

```sql
BEGIN;

SET LOCAL lock_timeout = '3s';
SET LOCAL statement_timeout = '10s';

-- 1. Önce route planı kilitle.
SELECT
    rp.id,
    rp.shipment_id,
    rp.status,
    rp.vehicle_id,
    rp.driver_id,
    rp.planned_start_at,
    rp.planned_end_at,
    rp.row_version
FROM route_plans AS rp
WHERE rp.id = :route_plan_id
FOR UPDATE;

-- Uygulama burada şunları kontrol eder:
-- - row_version == :expected_row_version
-- - status in ('Draft', 'Planned') ve command'e uygun state
-- - planned_end_at > planned_start_at

-- 2. Shipment parent'ı kilitle.
SELECT
    s.id,
    s.status,
    s.row_version
FROM shipments AS s
JOIN route_plans AS rp ON rp.shipment_id = s.id
WHERE rp.id = :route_plan_id
FOR UPDATE;
```

İlk SELECT route planını kilitler; ikinci SELECT shipment parent’ı aynı transaction’da kilitler. `Shipment` L2 source integrity’si tekrar okunur. Route plan `Shipment` ile yanlış bağlanmışsa transaction rollback edilir.

### 4.2 Vehicle row lock

```sql
-- 3. Vehicle kaynağını kilitle.
SELECT
    v.id,
    v.vehicle_type_id,
    v.plate_number,
    v.status,
    v.maintenance_until,
    v.row_version
FROM vehicles AS v
WHERE v.id = :vehicle_id
FOR UPDATE;
```

Bu SELECT’in amacı yalnızca vehicle alanlarını okumak değildir. Vehicle satırı, aynı kaynağı kullanmak isteyen farklı route transaction’ları için **serialization point** olur. Transaction A vehicle satırını tuttuğu sürece Transaction B aynı vehicle için `FOR UPDATE` bekler. A commit ettikten sonra B kendi overlap statement’ını yeni snapshot ile yeniden çalıştırmalıdır.

### 4.3 Driver row lock

```sql
-- 4. Driver kaynağını kilitle.
SELECT
    d.id,
    d.employee_id,
    d.full_name,
    d.license_number,
    d.license_expiry,
    d.is_active,
    d.row_version
FROM drivers AS d
WHERE d.id = :driver_id
FOR UPDATE;
```

Vehicle ve driver için her command aynı tablo sırasını kullanmalıdır: **vehicle sonra driver**. Alternatif olarak driver önce vehicle seçilebilir; önemli olan bütün write path’lerde tek bir sıranın korunmasıdır. Farklı endpoint’lerde farklı sıra kullanılmamalıdır.

## 5. Kilit sonrası uygunluk ve overlap sorguları

### 5.1 Vehicle status ve maintenance guard

```sql
SELECT
    v.status,
    v.maintenance_until,
    CASE
        WHEN v.status IN ('Maintenance', 'OutOfService')
            THEN 'VEHICLE_UNAVAILABLE'
        WHEN v.maintenance_until IS NOT NULL
             AND v.maintenance_until > :planned_start_at
            THEN 'VEHICLE_MAINTENANCE'
        ELSE NULL
    END AS rejection_code
FROM vehicles AS v
WHERE v.id = :vehicle_id;
```

`maintenance_until = planned_start_at` ise maintenance aralığının `[start,end)` yorumuna göre araç planın başlangıcında müsait kabul edilebilir; şirket operasyon politikası “başlangıçtan önce bakım tamamlanmış olmalı” diyorsa `>=` kuralı seçilmelidir. Bu karşılaştırma implementation’da tek bir domain policy method’unda toplanmalıdır.

### 5.2 Driver active/license guard

```sql
SELECT
    d.is_active,
    d.license_expiry,
    CASE
        WHEN d.is_active = false
            THEN 'DRIVER_INACTIVE'
        WHEN d.license_expiry IS NULL
            THEN 'DRIVER_LICENSE_MISSING'
        WHEN d.license_expiry < (:planned_end_at AT TIME ZONE 'UTC')::date
            THEN 'DRIVER_LICENSE_EXPIRED'
        ELSE NULL
    END AS rejection_code
FROM drivers AS d
WHERE d.id = :driver_id;
```

Ehliyet geçerliliği gün bazlıdır; route zamanları UTC timestamp, `license_expiry` ise date olabilir. Route’un bitiş günü ehliyetin son geçerli günü ise kabul edilecek şekilde `license_expiry < planned_end::date` kullanılmıştır. Şirket policy’si bitiş gününde ehliyet kullanımını yasaklarsa `<=` seçilebilir; bu karar kod ve testte sabitlenmelidir.

### 5.3 Vehicle schedule overlap

```sql
SELECT
    rp.id,
    rp.shipment_id,
    rp.status,
    rp.planned_start_at,
    rp.planned_end_at,
    rp.version
FROM route_plans AS rp
WHERE rp.vehicle_id = :vehicle_id
  AND rp.id <> :route_plan_id
  AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
  AND rp.planned_start_at IS NOT NULL
  AND rp.planned_end_at IS NOT NULL
  AND rp.planned_start_at < :candidate_end_at
  AND rp.planned_end_at > :candidate_start_at
ORDER BY rp.planned_start_at, rp.id;
```

Sonuç satırı varsa command `VEHICLE_SCHEDULE_CONFLICT` ile rollback edilir. `route_plan_id <> :route_plan_id` aynı route planın mevcut assignment’ını kendi kendisiyle çakıştırmamak içindir. Aynı shipment’ın eski ve yeni replan versiyonları özel olarak ayrıca ele alınmalıdır; aşağıdaki replan bölümünde bu konu açıklanmıştır.

### 5.4 Driver schedule overlap

```sql
SELECT
    rp.id,
    rp.shipment_id,
    rp.status,
    rp.planned_start_at,
    rp.planned_end_at,
    rp.version
FROM route_plans AS rp
WHERE rp.driver_id = :driver_id
  AND rp.id <> :route_plan_id
  AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
  AND rp.planned_start_at IS NOT NULL
  AND rp.planned_end_at IS NOT NULL
  AND rp.planned_start_at < :candidate_end_at
  AND rp.planned_end_at > :candidate_start_at
ORDER BY rp.planned_start_at, rp.id;
```

Vehicle ve driver overlap ayrı ayrı raporlanmalıdır. İkisini tek `OR` sorgusunda birleştirmek mümkün olsa da UI/API’ye hangi kaynağın çakıştığını açıklamak için ayrı result set veya `conflict_type` projection daha uygundur.

### 5.5 Tek sorguda conflict summary

```sql
WITH conflicts AS (
    SELECT
        'VEHICLE'::text AS resource_type,
        rp.id AS conflicting_route_plan_id,
        rp.shipment_id,
        rp.status,
        rp.planned_start_at,
        rp.planned_end_at
    FROM route_plans AS rp
    WHERE rp.vehicle_id = :vehicle_id
      AND rp.id <> :route_plan_id
      AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
      AND rp.planned_start_at < :candidate_end_at
      AND rp.planned_end_at > :candidate_start_at

    UNION ALL

    SELECT
        'DRIVER'::text AS resource_type,
        rp.id AS conflicting_route_plan_id,
        rp.shipment_id,
        rp.status,
        rp.planned_start_at,
        rp.planned_end_at
    FROM route_plans AS rp
    WHERE rp.driver_id = :driver_id
      AND rp.id <> :route_plan_id
      AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
      AND rp.planned_start_at < :candidate_end_at
      AND rp.planned_end_at > :candidate_start_at
)
SELECT *
FROM conflicts
ORDER BY resource_type, planned_start_at, conflicting_route_plan_id;
```

Bu sorgu yalnızca kilit alınmış vehicle/driver kaynaklarının güncel overlap görünümünü okuduktan sonra çalıştırılmalıdır. Transaction’ın başında yapılan “preflight” sorgusu nihai doğrulama değildir.

## 6. Tam assignment transaction örneği

Aşağıdaki örnek, route planı, shipment, vehicle ve driver’ı aynı transaction’da kilitler; sonra status/license/schedule kontrolü yapar; başarılıysa assignment’ı commit eder. Uygulama kodu SQL sonuçlarını domain error’a çevirmelidir.

```sql
BEGIN;

SET LOCAL lock_timeout = '3s';
SET LOCAL statement_timeout = '15s';

-- A. RoutePlan lock + optimistic version check.
SELECT
    rp.id,
    rp.shipment_id,
    rp.status,
    rp.vehicle_id,
    rp.driver_id,
    rp.planned_start_at,
    rp.planned_end_at,
    rp.row_version
FROM route_plans AS rp
WHERE rp.id = :route_plan_id
FOR UPDATE;

-- A uygulama guard'ları:
-- row_version == :expected_row_version
-- status == 'Draft'
-- planned start/end dolu ve end > start

-- B. Parent shipment lock.
SELECT
    s.id,
    s.status,
    s.row_version
FROM shipments AS s
JOIN route_plans AS rp ON rp.shipment_id = s.id
WHERE rp.id = :route_plan_id
FOR UPDATE;

-- B uygulama guard'ı:
-- shipment.status IN ('Preparing', 'Ready')

-- C. Vehicle lock. Bütün writer'lar vehicle'ı driver'dan önce kilitler.
SELECT
    v.id,
    v.status,
    v.maintenance_until,
    v.row_version
FROM vehicles AS v
WHERE v.id = :vehicle_id
FOR UPDATE;

-- D. Driver lock.
SELECT
    d.id,
    d.is_active,
    d.license_expiry,
    d.row_version
FROM drivers AS d
WHERE d.id = :driver_id
FOR UPDATE;

-- E. Vehicle guard.
SELECT 1
FROM vehicles AS v
WHERE v.id = :vehicle_id
  AND v.status NOT IN ('Maintenance', 'OutOfService')
  AND (
      v.maintenance_until IS NULL
      OR v.maintenance_until <= :planned_start_at
  );
-- Satır yoksa ROLLBACK + VEHICLE_MAINTENANCE/VEHICLE_UNAVAILABLE.

-- F. Driver guard.
SELECT 1
FROM drivers AS d
WHERE d.id = :driver_id
  AND d.is_active = true
  AND d.license_expiry IS NOT NULL
  AND d.license_expiry >= (:planned_end_at AT TIME ZONE 'UTC')::date;
-- Satır yoksa ROLLBACK + DRIVER_INACTIVE/DRIVER_LICENSE_EXPIRED.

-- G. Vehicle overlap. Bu sorgu resource lock alındıktan sonra yapılır.
SELECT rp.id
FROM route_plans AS rp
WHERE rp.vehicle_id = :vehicle_id
  AND rp.id <> :route_plan_id
  AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
  AND rp.planned_start_at < :planned_end_at
  AND rp.planned_end_at > :planned_start_at
LIMIT 1;
-- Satır varsa ROLLBACK + VEHICLE_SCHEDULE_CONFLICT.

-- H. Driver overlap.
SELECT rp.id
FROM route_plans AS rp
WHERE rp.driver_id = :driver_id
  AND rp.id <> :route_plan_id
  AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
  AND rp.planned_start_at < :planned_end_at
  AND rp.planned_end_at > :planned_start_at
LIMIT 1;
-- Satır varsa ROLLBACK + DRIVER_SCHEDULE_CONFLICT.

-- I. Assignment update.
UPDATE route_plans
SET vehicle_id = :vehicle_id,
    driver_id = :driver_id,
    updated_at = now(),
    row_version = row_version + 1
WHERE id = :route_plan_id;

-- J. Araç status projection. Source of truth RoutePlan assignment'tır;
-- bu alan operasyon board için projection olarak tutuluyorsa update edilir.
UPDATE vehicles
SET status = CASE
                 WHEN status = 'Available' THEN 'Assigned'
                 ELSE status
             END,
    current_route_plan_id = :route_plan_id,
    last_status_at = now(),
    row_version = row_version + 1
WHERE id = :vehicle_id;

-- K. Driver status projection isteniyorsa ayrıca açık policy gerekir.
-- Driver'ı Assigned state'e çevirmek zorunlu değildir; assignment history
-- route_plans üzerinden okunabilir.

-- L. Audit + outbox + idempotency aynı transaction'da.
INSERT INTO audit_logs (
    id, entity_type, entity_id, action, actor_user_id,
    correlation_id, payload_json, created_at
)
VALUES (
    gen_random_uuid(), 'RoutePlan', :route_plan_id,
    'RouteResourcesAssigned', :actor_id,
    :correlation_id, :audit_payload::jsonb, now()
);

-- Idempotency result application repository'nin mevcut şemasına göre yazılır.
-- Aynı command'ın response snapshot'ı ve payload hash'i saklanmalıdır.

COMMIT;
```

Bu SQL’de `UPDATE vehicles` bir projection olarak kullanılmıştır. Eğer `vehicles.status` gerçek state source of truth olarak kullanılacaksa, yalnızca route assignment’ın başarılı olduğu transaction içinde güncellenmeli ve route tamamlandığında `Available` transition’ı ayrı explicit command ile yapılmalıdır. Aynı vehicle’ın iki aktif route planına projection olarak bağlanmasına izin verilmemelidir.

## 7. ETag/row_version kontrolü

`FOR UPDATE` pessimistic lock, stale HTTP request’i tek başına reddetmez; route plan row version’ı ayrıca kontrol edilmelidir. Önerilen kontrol:

```sql
BEGIN;

SELECT id, status, row_version
FROM route_plans
WHERE id = :route_plan_id
FOR UPDATE;

-- Application:
-- if actual_row_version <> :expected_row_version:
--     ROLLBACK + RESOURCE_VERSION_CONFLICT

UPDATE route_plans
SET vehicle_id = :vehicle_id,
    driver_id = :driver_id,
    row_version = row_version + 1,
    updated_at = now()
WHERE id = :route_plan_id
  AND row_version = :expected_row_version
RETURNING id, row_version;

-- RETURNING row gelmezse:
-- ROLLBACK + RESOURCE_VERSION_CONFLICT

COMMIT;
```

`SELECT FOR UPDATE` sonrası aynı transaction’da version değişmemelidir; `WHERE row_version = expected` yine de defense-in-depth sağlar. API response yeni version’ı ETag olarak döndürür:

```http
ETag: "7"
```

Stale ETag için otomatik aynı payload retry yapılmaz. Client fresh GET yapmalı ve kullanıcının güncel route/resource state’ini onaylaması gerekir [1].

## 8. İki bağlantılı yarış senaryosu

### 8.1 Yarış setup

İki route planı aynı vehicle ve driver’ı kullanmak istiyor:

```text
Vehicle V-01
Driver  D-01

Route A: 2026-08-17 08:00–12:00
Route B: 2026-08-17 10:00–14:00
```

### 8.2 Connection A

```sql
BEGIN;

SELECT id, row_version
FROM route_plans
WHERE id = :route_a
FOR UPDATE;

SELECT id, status
FROM shipments
WHERE id = :shipment_a
FOR UPDATE;

SELECT id, status
FROM vehicles
WHERE id = :vehicle_v01
FOR UPDATE;

SELECT id, is_active
FROM drivers
WHERE id = :driver_d01
FOR UPDATE;

-- A overlap sorgusunu çalıştırır; sonuç yok.
-- A route_a assignment update yapar.

UPDATE route_plans
SET vehicle_id = :vehicle_v01,
    driver_id = :driver_d01,
    status = 'Planned',
    row_version = row_version + 1
WHERE id = :route_a;

-- A burada henüz COMMIT etmeden bekleyebilir.
```

### 8.3 Connection B

```sql
BEGIN;

SELECT id, row_version
FROM route_plans
WHERE id = :route_b
FOR UPDATE;

SELECT id, status
FROM shipments
WHERE id = :shipment_b
FOR UPDATE;

-- B vehicle lock'ta bekler:
SELECT id, status
FROM vehicles
WHERE id = :vehicle_v01
FOR UPDATE;
```

Connection B’nin `vehicle` SELECT’i A’nın vehicle row lock’ını bekler. A commit ettiğinde B devam eder. B’nin ilk snapshot’ı eski olsa bile **kilit sonrası overlap query yeni statement olarak yeniden çalıştırılmalıdır**:

```sql
SELECT rp.id, rp.planned_start_at, rp.planned_end_at
FROM route_plans AS rp
WHERE rp.vehicle_id = :vehicle_v01
  AND rp.id <> :route_b
  AND rp.status IN ('Draft', 'Planned', 'Locked', 'InProgress')
  AND rp.planned_start_at < TIMESTAMPTZ '2026-08-17 14:00:00+00'
  AND rp.planned_end_at > TIMESTAMPTZ '2026-08-17 10:00:00+00';
```

Bu sorgu Route A’yı görür ve B şu sonucu üretir:

```text
ROLLBACK
API 409 VEHICLE_SCHEDULE_CONFLICT
```

Driver overlap da aynı şekilde Route A’yı gösterir. API response’ta `resourceType = Vehicle`, `conflictingRoutePlanId`, planlanan zaman aralığı ve kullanıcı eylemi bulunmalıdır.

### 8.4 Beklenen sonuç tablosu

| Olay | Connection A | Connection B |
|---|---|---|
| RoutePlan lock | Başarılı | Kendi route planını kilitler |
| Vehicle lock | Başarılı | A’yı bekler |
| A overlap | Yok | — |
| A update/commit | Başarılı | — |
| B vehicle lock sonrası reread | — | Route A görünür |
| B sonucu | — | `409 VEHICLE_SCHEDULE_CONFLICT` |
| Stock movement | Yok | Yok |
| Route B partial write | Yok | Yok |

### 8.5 Aynı zaman sınırı

```text
Route A: [08:00, 10:00)
Route B: [10:00, 12:00)
```

Overlap koşulu false olur; B kabul edilebilir. Bu sınırın SQL, domain unit ve integration testlerinde aynı şekilde uygulanması zorunludur.

## 9. Race olmaması için kaçınılması gereken SQL desenleri

### 9.1 Lock’suz check-then-insert

```sql
-- Güvensiz: hiçbir resource row kilitlenmiyor.
SELECT 1
FROM route_plans
WHERE vehicle_id = :vehicle_id
  AND planned_start_at < :end_at
  AND planned_end_at > :start_at;

-- İki transaction da boş sonuç görebilir.
INSERT INTO route_plans (...);
```

Bu desen yalnızca application-level check’e dayanır ve concurrent phantom insert’e açıktır.

### 9.2 `SKIP LOCKED` ile assignment

```sql
-- Assignment için önerilmez.
SELECT id
FROM vehicles
WHERE id = :vehicle_id
FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED`, kilitli kaynağı “meşgul” şeklinde raporlamak yerine görünmez yapabilir. Bu davranış queue/worker candidate taraması için uygun olabilir; belirli araç/şoför atama command’inde kullanıcıya hangi kaynağın çakıştığını göstermeyi zorlaştırır ve yanlışlıkla alternatif seçime yol açabilir. Normal assignment path’inde `FOR UPDATE` ile bekleme ve timeout policy tercih edilmelidir.

### 9.3 Sadece route plan row lock

```sql
-- Yetersiz: A ve B farklı route plan satırlarını kilitler.
SELECT id
FROM route_plans
WHERE id = :route_plan_id
FOR UPDATE;

-- Sonrasında iki transaction aynı vehicle'a yazabilir.
```

Paylaşılan resource row (`vehicles.id`, `drivers.id`) kilitlenmeden farklı route plan’lar birbirini serialize etmez.

## 10. Exclusion constraint seçeneği

Row lock bütün application writers için zorunlu olmalıdır. Buna ek olarak PostgreSQL exclusion constraint, unutulmuş bir writer veya gelecekteki farklı command path’i için database-level defense-in-depth sağlar. Bunun için `btree_gist` extension ve route plan üzerinde generated/stored `tstzrange` alanı kullanılabilir.

### 10.1 Active route window

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE route_plans
    ADD COLUMN IF NOT EXISTS planned_window tstzrange
    GENERATED ALWAYS AS (
        CASE
            WHEN planned_start_at IS NULL OR planned_end_at IS NULL
                THEN NULL
            ELSE tstzrange(planned_start_at, planned_end_at, '[)')
        END
    ) STORED;

CREATE INDEX IF NOT EXISTS ix_route_plans_vehicle_window
    ON route_plans USING gist (vehicle_id, planned_window);

CREATE INDEX IF NOT EXISTS ix_route_plans_driver_window
    ON route_plans USING gist (driver_id, planned_window);
```

### 10.2 Vehicle exclusion

```sql
ALTER TABLE route_plans
    ADD CONSTRAINT ex_route_plans_vehicle_window
    EXCLUDE USING gist (
        vehicle_id WITH =,
        planned_window WITH &&
    )
    WHERE (
        vehicle_id IS NOT NULL
        AND planned_window IS NOT NULL
        AND status IN ('Draft', 'Planned', 'Locked', 'InProgress')
    );
```

### 10.3 Driver exclusion

```sql
ALTER TABLE route_plans
    ADD CONSTRAINT ex_route_plans_driver_window
    EXCLUDE USING gist (
        driver_id WITH =,
        planned_window WITH &&
    )
    WHERE (
        driver_id IS NOT NULL
        AND planned_window IS NOT NULL
        AND status IN ('Draft', 'Planned', 'Locked', 'InProgress')
    );
```

Bu constraint’ler iki önemli tasarım gerektirir:

1. `status` değişiklikleri exclusion kapsamına giren veya çıkan bir update olduğundan, route status transition’ları da aynı transaction ve retry policy ile ele alınmalıdır.
2. Replan sırasında eski locked version ve yeni version aynı resource/zaman aralığını kısa süreli birlikte taşıyacaksa exclusion constraint yeni version insert’ini reddeder. Bu nedenle replan için eski planın ne zaman `Superseded` olacağı veya kaynakların ne zaman ayrılacağı explicit state/transaction tasarımında belirlenmelidir.

### 10.4 Exclusion constraint ve replan kararı

İlk implementation için öneri:

```text
Locked old plan
→ New Draft replanned_from old plan, resourcesiz oluştur
→ New plan’a farklı/uygun resources ata
→ New plan Planned/Locked olduğunda old plan Superseded yap
```

`copyResources = true` yalnızca eski plan ve yeni plan aynı anda resource reservation tutmayacak şekilde özel transaction ile uygulanmalıdır. Aksi halde constraint güvenli biçimde yeni planı reddedecektir. Daha basit ve açıklanabilir MVP davranışı `copyResources = false` kabul etmek ve kaynakları yeni plan için tekrar atamaktır.

### 10.5 Constraint violation mapping

PostgreSQL SQLSTATE `23P01` exclusion constraint violation’dır. Constraint adı üzerinden kaynak ayrımı yapılabilir:

| Constraint | API code |
|---|---|
| `ex_route_plans_vehicle_window` | `VEHICLE_SCHEDULE_CONFLICT` |
| `ex_route_plans_driver_window` | `DRIVER_SCHEDULE_CONFLICT` |
| `ux_route_plans_shipment_version` | `ROUTE_VERSION_CONFLICT` |
| vehicle plate unique | `VEHICLE_PLATE_ALREADY_EXISTS` |
| driver license unique | `DRIVER_LICENSE_ALREADY_EXISTS` |

SQLSTATE ve constraint name response’a ham biçimde taşınmaz; application layer typed ProblemDetails’a çevirir.

## 11. Constraint olmadan row-lock yeterli mi?

Evet, aşağıdaki koşullar sağlanıyorsa row lock + post-lock reread `READ COMMITTED` altında yeterli olabilir:

| Koşul | Zorunluluk |
|---|---|
| Her vehicle-assignment writer vehicle row’ını `FOR UPDATE` kilitliyor | Evet |
| Her driver-assignment writer driver row’ını `FOR UPDATE` kilitliyor | Evet |
| Lock sonrasında overlap tekrar okunuyor | Evet |
| Tüm status/interval writer’ları aynı lock order kullanıyor | Evet |
| Route insert/update aynı transaction’da | Evet |
| Lock alınmadan önce yapılan preflight nihai karar sayılmıyor | Evet |
| Background cleanup/status worker aynı lock protocol’ü izliyor | Evet |

Constraint eklenmesi, unutulan writer’lara karşı ek güvenlik sağlar; ancak exclusion constraint tek başına UI/API conflict detayını ve deterministic business retry davranışını sağlamaz. Önerilen production baseline: **row lock + post-lock reread + exclusion constraint**.

## 12. Deadlock ve timeout yönetimi

### 12.1 Lock timeout

Normal command lock beklemelidir; sınırsız bekleme kabul edilmez:

```sql
SET LOCAL lock_timeout = '3s';
SET LOCAL statement_timeout = '15s';
```

`55P03 lock_not_available` yalnızca `NOWAIT` veya timeout kullanıldığında gelebilir. API’de `RESOURCE_LOCK_TIMEOUT` veya `TRANSACTION_LOCK_TIMEOUT` olarak 409/503 mapping seçilebilir. Kullanıcıya işlemi tekrar denemesi veya farklı resource seçmesi söylenir; transaction’ın yarım update bırakmadığı garanti edilir.

### 12.2 Deadlock

PostgreSQL deadlock SQLSTATE `40P01` döndürür. Uygulama:

1. Transaction’ı rollback eder.
2. Yalnızca idempotency key bulunan command’lerde en fazla sınırlı sayıda fresh transaction retry eder.
3. Her retry’de route, vehicle, driver ve version yeniden okunur.
4. Conflict/business error varsa retry yerine typed ProblemDetails döner.
5. Aynı transaction instance yeniden kullanılmaz.

```text
40P01 → rollback → jitter 20–100 ms → fresh transaction → max 2 retry
40001 → rollback → fresh transaction → max 2 retry
23505/23P01 → rollback → retry yok; typed resource conflict
```

### 12.3 Isolation upgrade ne zaman gerekir?

Aynı resource row’ı tüm writer’lar kilitliyorsa assignment için `SERIALIZABLE` zorunlu değildir. Şu durumlarda ayrıca değerlendirilebilir:

- Bir command tek seferde birden fazla araç/şoför kaynağı seçiyorsa.
- Route resource reservations ayrı tabloya taşınır ve bütün kaynaklar ortak row üzerinden serialize edilemiyorsa.
- Birden fazla aggregate’ın global kapasite veya slot bütçesi aynı anda güncelleniyorsa.

Bu durumda serialization failure `40001` olarak typed conflict/retry policy’ye alınmalıdır. Genel MVP’de default `READ COMMITTED` korunur [1].

## 13. Transaction sonrası gözlemleme sorguları

### 13.1 Bekleyen lock’ları görme

```sql
SELECT
    blocked.pid AS blocked_pid,
    blocked.query AS blocked_query,
    blocking.pid AS blocking_pid,
    blocking.query AS blocking_query,
    now() - blocking.query_start AS blocking_for,
    blocked.wait_event_type,
    blocked.wait_event
FROM pg_stat_activity AS blocked
JOIN pg_locks AS blocked_lock
  ON blocked_lock.pid = blocked.pid
 AND NOT blocked_lock.granted
JOIN pg_locks AS blocking_lock
  ON blocking_lock.locktype = blocked_lock.locktype
 AND blocking_lock.database IS NOT DISTINCT FROM blocked_lock.database
 AND blocking_lock.relation IS NOT DISTINCT FROM blocked_lock.relation
 AND blocking_lock.page IS NOT DISTINCT FROM blocked_lock.page
 AND blocking_lock.tuple IS NOT DISTINCT FROM blocked_lock.tuple
 AND blocking_lock.virtualxid IS NOT DISTINCT FROM blocked_lock.virtualxid
 AND blocking_lock.transactionid IS NOT DISTINCT FROM blocked_lock.transactionid
 AND blocking_lock.classid IS NOT DISTINCT FROM blocked_lock.classid
 AND blocking_lock.objid IS NOT DISTINCT FROM blocked_lock.objid
 AND blocking_lock.objsubid IS NOT DISTINCT FROM blocked_lock.objsubid
 AND blocking_lock.pid <> blocked_lock.pid
JOIN pg_stat_activity AS blocking
  ON blocking.pid = blocking_lock.pid
WHERE blocked.wait_event_type = 'Lock';
```

### 13.2 Uzun transaction ve route lock gözlemi

```sql
SELECT
    pid,
    usename,
    application_name,
    client_addr,
    state,
    xact_start,
    query_start,
    now() - xact_start AS transaction_age,
    wait_event_type,
    wait_event,
    left(query, 240) AS query_preview
FROM pg_stat_activity
WHERE datname = current_database()
ORDER BY xact_start NULLS LAST;
```

Assignment transaction’larının lock beklemesi ölçülmelidir. Uzun süre açık kalan web request transaction’ları route/vehicle kaynaklarını gereksiz bloklayabilir; transaction içine dış HTTP, mail, map provider veya dosya upload çağrısı alınmamalıdır.

## 15. Integration test SQL senaryoları

### 15.1 Aynı araçta yalnızca bir commit

Test fixture iki ayrı database connection açmalıdır. Her connection kendi transaction’ında farklı route planı kilitler, aynı vehicle satırına `FOR UPDATE` alır ve overlap kontrolü yapar. İlk commit ettikten sonra ikinci connection overlap görmeli ve rollback etmelidir.

```sql
-- Connection A
BEGIN;
SELECT id FROM route_plans WHERE id = :route_a FOR UPDATE;
SELECT id FROM shipments WHERE id = :shipment_a FOR UPDATE;
SELECT id FROM vehicles WHERE id = :vehicle FOR UPDATE;
SELECT id FROM drivers WHERE id = :driver FOR UPDATE;
-- overlap yok
UPDATE route_plans
SET vehicle_id = :vehicle, driver_id = :driver, status = 'Planned'
WHERE id = :route_a;
-- test synchronization barrier
COMMIT;
```

```sql
-- Connection B
BEGIN;
SELECT id FROM route_plans WHERE id = :route_b FOR UPDATE;
SELECT id FROM shipments WHERE id = :shipment_b FOR UPDATE;
-- burada vehicle lock beklenir
SELECT id FROM vehicles WHERE id = :vehicle FOR UPDATE;
SELECT id FROM drivers WHERE id = :driver FOR UPDATE;

-- lock sonrası yeni statement; Route A artık görünür
SELECT 1
FROM route_plans
WHERE vehicle_id = :vehicle
  AND id <> :route_b
  AND status IN ('Draft', 'Planned', 'Locked', 'InProgress')
  AND planned_start_at < :route_b_end
  AND planned_end_at > :route_b_start;

-- test assertion: row vardır
ROLLBACK;
```

### 15.2 Aynı vehicle, farklı zaman aralıkları

```sql
-- A: [08:00, 10:00)
-- B: [10:00, 12:00)
-- overlap predicate false; iki command commit edebilir.
```

Bu senaryo, bitiş başlangıca eşit olduğunda sistemin gereksiz conflict üretmediğini doğrular.

### 15.3 Aynı driver, farklı vehicle

Aynı driver iki farklı route’a aynı zaman aralığında atanır. Vehicle lock’ları farklı olsa bile her iki transaction aynı driver row’ını kilitler. İkinci transaction driver lock sonrası overlap görür ve `DRIVER_SCHEDULE_CONFLICT` döner.

### 15.4 Stale ETag

```sql
BEGIN;
SELECT row_version
FROM route_plans
WHERE id = :route_plan_id
FOR UPDATE;

-- expected = 5, actual = 6
ROLLBACK;
```

Test sonucu `409 RESOURCE_VERSION_CONFLICT`; vehicle/driver assignment, audit ve idempotency side effect’i oluşmamalıdır.

### 15.5 Lock timeout

```sql
BEGIN;
SET LOCAL lock_timeout = '100ms';
SELECT id FROM vehicles WHERE id = :vehicle_id FOR UPDATE;
-- Eğer başka transaction kilidi tutuyorsa SQLSTATE 55P03
ROLLBACK;
```

Production command timeout’u testte kısa tutulabilir; normal uygulama timeout’u operasyonel latency hedefiyle belirlenmelidir.

## 16. Implementation gate

Araç/şoför assignment slice’ı aşağıdaki koşullar sağlanmadan tamamlanmış sayılmamalıdır:

| Gate | Beklenen kanıt |
|---|---|
| Domain | Vehicle/Driver availability ve RoutePlan assignment guard unit testleri |
| SQL model | row_version, status check, route version unique, schedule index/exclusion kararı |
| Lock order | RoutePlan → Shipment → Vehicle → Driver tüm writer’larda aynı |
| Reread | Vehicle/driver lock sonrası overlap sorgusu tekrar çalışıyor |
| Concurrency | İki PostgreSQL connection testinde yalnızca bir assignment commit ediyor |
| Boundary | `[start,end)` ve exact boundary testleri geçiyor |
| ETag | Stale `If-Match` 409 ve side effect yok |
| Idempotency | Aynı key replay, farklı payload mismatch |
| Error mapping | SQLSTATE/constraint/domain typed ProblemDetails |
| Audit | Başarılı assignment ve conflict correlation/audit stratejisi |
| Security | Gerçek login, route-manage/read-only/anonymous ve IDOR testleri |
| Observability | Lock wait, transaction age ve deadlock log alanları mevcut |

## 17. Önerilen implementation kararı

MVP için önerilen sağlam baseline şudur:

```text
READ COMMITTED
+ RoutePlan → Shipment → Vehicle → Driver fixed lock order
+ Vehicle/Driver FOR UPDATE
+ Lock sonrası overlap re-read
+ row_version + ETag
+ Idempotency-Key before transaction
+ bounded deadlock/serialization retry
+ PostgreSQL exclusion constraint as defense-in-depth
+ typed ProblemDetails
```

`SKIP LOCKED` assignment path’inde kullanılmamalı, `SERIALIZABLE` bütün sistem için varsayılan yapılmamalı ve yalnızca UI tarafındaki conflict kontrolüne güvenilmemelidir. Exclusion constraint eklenecekse replan sırasında eski locked version ile yeni version’ın aynı kaynağı aynı anda rezerve etmemesi için `Superseded`/resource reservation lifecycle kararı migration’dan önce kapatılmalıdır.
