# G6.2 Araç, Şoför ve Manuel Rotalama Teknik Tasarımı

**Tarih:** 2026-08-16
**Durum:** Kodlama öncesi technical design gate
**Bağımlılık:** L2 `Issued DeliveryNote → Shipment`
**Kapsam:** Araç tipi, effective kapasite profili, gerçek araç, şoför, manuel rota/durak ve araç/şoför zaman çakışması

## 1. Amaç ve bounded slice sınırı

Bu slice’ın amacı, L2 ile oluşturulan `Shipment` kaydını güvenilir bir araç, şoför ve sıralı müşteri teslim duraklarıyla ilişkilendirmektir. Slice, rota planını **manuel veya kullanıcı tarafından verilen sıra** ile oluşturur; trafik sağlayıcısı, geocoding, kesin en kısa rota, araç kapasite-fit algoritması, mixed pallet, barkodlu yükleme ve teslimat kanıtı üretmez.

O-014 gereği araç kapasitesi ve rota erişimi ileride kargo planlama tarafından kullanılacaktır; ancak bu slice’ta araç için yalnızca **master data ve zamanlama uygunluğu** doğrulanır. Fiziksel `kg`, `m³`, palet, kapı, zemin, istifleme ve aks uygunluğu `LoadPlan/VehicleFitEvaluation` slice’ına aittir. İlk sürüm matematiksel olarak optimal rota veya 3D yükleme garantisi vermez [1] [2].

```text
L2 Shipment(Preparing/Ready)
  → RoutePlan(Draft)
      → RouteStop(customer + address + sequence)
      → Vehicle + Driver assignment
      → RoutePlan(Planned)
      → RoutePlan(Locked)
```

Bu bounded slice’ın sonunda shipment henüz `Loaded` veya `InTransit` olmaz. Route lock, sevkiyatın yüklenmeye hazır bir operasyon planına sahip olduğunu gösterir; gerçek yükleme ve çıkış sonraki slice’tır.

## 2. Mevcut repository durumu

Mevcut source tree’de delivery note, invoice, current account, production ve warehouse transfer implementation’ları vardır; ancak araç, şoför, route plan veya route stop entity/service/controller/policy implementation’ı bulunmamaktadır. Canonical SQL ve API belgeleri hedef tablo ve endpoint yönünü tanımlar, fakat bunlar henüz runtime contract değildir.

L2 shipment sözleşmesinde shipment kaynağı tek bir `Issued DeliveryNote` olarak tanımlanmıştır. Bu slice yeni stok movement oluşturmayacak, delivery note miktarını değiştirmeyecek ve shipment item’larını yeniden hesaplamayacaktır. Route plan yalnızca mevcut shipment’a operasyonel bağlam ekleyecektir [3].

## 3. Bounded context ve source of truth

### 3.1 Shipping sorumlulukları

| Kavram | Source of truth | Bu slice’taki rol |
|---|---|---|
| `VehicleType` | Araç tipi kimliği ve isim | Tip ana verisi; fiziksel effective değerler kapasite profilinden okunur |
| `VehicleCapacity` | Effective fiziksel kapasite profili | Gelecek LoadPlan için kapasite snapshot kaynağı |
| `Vehicle` | Plaka, operasyon durumu, bakım aralığı | Route assignment uygunluğu ve durum geçmişi |
| `Driver` | Operasyonel şoför, ehliyet ve aktiflik | Route assignment uygunluğu |
| `Shipment` | L2 shipment | RoutePlan’ın parent kaydı |
| `RoutePlan` | Shipment’ın rota versiyonu, zaman aralığı, araç/şoför ataması | Bu slice’ın ana aggregate sınırı |
| `RouteStop` | Müşteri + canonical adres + sıra | Manuel teslim durakları |
| `Employee` | İK/personel ana verisi | Driver’a opsiyonel bağlantı; şoför ehliyet kaydının yerine geçmez |
| `CustomerAddress` | Müşteri teslim adresi | RouteStop serbest metin adresinin yerine geçer |

`Vehicle.status`, `Shipment.status`, `RoutePlan.status` ve `RouteStop.status` ayrı state machine’lerdir. Bir aracın `Assigned` olması shipment’ı `Loaded` yapmaz; route lock da stok hareketi oluşturmaz [4].

### 3.2 Driver–Employee sınırı

`Driver`, taşıma operasyonu için ehliyet, aktiflik ve atama uygunluğunu taşır. `Employee`, İK/personel master’ıdır. İlk implementation’da `drivers.employee_id` nullable kalabilir; Employee modülü henüz yokken operasyonel şoför kartı çalışır. `employee_id` doluysa Employee kaydıyla ilişki doğrulanır, ancak ehliyet alanlarının source of truth’u Driver’da kalır.

`full_name` operasyonel ekranda zorunlu gösterim alanıdır. Employee ile bağlantı kurulduğunda personel adı sessizce kopyalanmamalı; API response controlled projection ile Driver/Employee bilgilerini birleştirmelidir. Geçmiş rota kayıtları canlı personel master’ı değiştiğinde bozulmaması için assignment snapshot’ı ileride eklenebilir; bu snapshot L3 route lock için zorunlu değildir.

## 4. Domain modeli ve invariant’lar

### 4.1 VehicleType

`VehicleType` bir araç sınıfının kimlik ve referans kaydıdır. Önerilen source-of-truth ayrımı şöyledir:

```text
VehicleType
  - code
  - name
  - is_active

VehicleCapacity
  - vehicle_type_id
  - effective_from / effective_to
  - dimensions, door, weight, volume, pallet, height, floor policy
  - capacity_policy_snapshot
```

Canonical SQL taslağında bazı kapasite alanları hem `vehicle_types` hem `vehicle_capacities` içinde tekrar edilmektedir [5]. Bu duplicate source-of-truth riski nedeniyle implementation migration’ında ölçü ve kapasite alanlarının effective `VehicleCapacity` altında tutulması önerilir. `VehicleType` yalnızca tipi tanımlar; geçmiş planlar `capacity_snapshot` ile korunur.

### 4.2 VehicleCapacity

Bir effective kapasite profili için minimum alanlar şunlardır:

| Alan grubu | Alanlar | L3 kullanımı |
|---|---|---|
| İç ölçü | `inner_length`, `inner_width`, `inner_height` | L4 vehicle fit için hazır kaynak |
| Kapı | `door_width`, `door_height`, `door_depth` | L4 hard constraint |
| Ağırlık | `max_gross_weight`, `tare_weight`, `max_payload_weight` | L4 kapasite |
| Hacim | `max_usable_volume` | L4 kapasite |
| Zemin | `floor_length`, `floor_width`, `floor_load_limit` | L4 fit |
| Palet | `max_pallet_count`, allowed pallet types | L4 fit |
| İstif | `max_load_height`, `max_stack_count` | L4 fit |
| Erişim | loading/unloading sides, door count | L4 stop access |
| Dağılım | axle/load-zone policy | Veri yoksa `NotEvaluated` |

Bu slice kapasiteyi doğrulamaz; yalnızca route assignment response’unda **hangi effective profile’ın seçili olduğunu** gösterir. `VehicleCapacity.effective_to` değeri `effective_from` değerinden sonra olmalıdır. Aynı `VehicleType` için geçerlilik aralıkları çakışmamalıdır.

### 4.3 Vehicle state machine

```text
Available → Assigned → Loading → InTransit → Available
Available → Maintenance
Available/Maintenance → OutOfService
```

Bu bounded slice yalnızca master/status command’lerini ve route assignment ile `Available → Assigned` geçişini kapsar. `Loading`, `InTransit` ve dönüş transition’ları gerçek yükleme/çıkış workflow’unda uygulanmalıdır.

| Kural | Davranış |
|---|---|
| Inactive veya `OutOfService` araç | Assignment reddedilir |
| `Maintenance` veya `maintenance_until > planned_start_at` | Assignment reddedilir |
| Route zaman aralığı başka aktif planla çakışıyor | Assignment reddedilir |
| Araç tipi inactive | Yeni araç oluşturma/assignment reddedilir |
| Capacity profile yok | Master kayıt oluşturulabilir; route lock policy’ye göre reddedilir veya açık uyarı üretir |
| `plate_number` | Normalize edilmiş aktif plaka unique olmalıdır |

Araç durumunun UI üzerinden serbest PATCH ile değiştirilmesine izin verilmez. `POST /vehicles/{id}/status` gibi explicit command kullanılır ve audit üretilir.

### 4.4 Driver state machine

```text
Active → Suspended
Active → Inactive
Suspended → Active
```

Şoför route lock sırasında aşağıdaki kontrollerden geçmelidir:

- `is_active = true` veya status `Active`.
- Ehliyet numarası policy’ye göre dolu ve normalize edilmiş olmalı.
- `license_expiry >= planned_end_at` tarihinin gün karşılığı olmalı.
- Aynı zaman aralığında başka aktif route plan ile çakışmamalı.
- `employee_id` doluysa Employee mevcut ve aktif olmalı.

Sadece route assignment yapmak şoförün çalışma süresini veya puantajını yazmaz; bu entegrasyon Employees/Attendance bounded context’ine aittir.

### 4.5 RoutePlan aggregate

RoutePlan, Shipment’ın versioned manual route aggregate’ıdır. Aggregate child collection’ları domain tarafında private backing field ile tutulmalı; controller doğrudan stop collection mutate etmemelidir.

```text
Draft → Planned → Locked
  └──────────────→ Exception
Locked → yeni version ile Replanned
```

Bu slice’ta `InProgress` ve `Completed` state’leri yalnızca gelecekteki delivery/driver operation komutları için ayrılmıştır; uygulanmaz.

| State | Anlam | Bu slice’taki işlem |
|---|---|---|
| `Draft` | Duraklar ve kaynaklar düzenleniyor | Stop ekleme/silme/sıralama, kaynak atama |
| `Planned` | Zorunlu route alanları ve zaman penceresi geçerli | Lock için hazır |
| `Locked` | Rota versiyonu değiştirilemez | Yeni replan version gerekir |
| `Exception` | Rota planında operasyonel istisna var | İleride teslim/araç akışı kullanır |

RoutePlan invariant’ları:

1. `shipment_id` zorunludur ve L2 shipment mevcut olmalıdır.
2. Aynı shipment için aynı `version` yalnızca bir kez bulunabilir.
3. `planned_end_at > planned_start_at` olmalıdır.
4. Lock için araç ve şoför zorunludur.
5. Lock için en az bir RouteStop bulunmalıdır.
6. Stop sequence `1..N` biçiminde boşluksuz ve unique olmalıdır.
7. Kilitli route plan üzerinde stop, araç, şoför veya zaman doğrudan değiştirilemez.
8. Replan yeni `version`, `replanned_from_id`, reason ve audit üretir.
9. RoutePlan route lock, Shipment status’unu `Loaded` yapmaz.
10. Rota değişikliği DeliveryNote, Stock veya Invoice state’lerini doğrudan değiştirmez.

### 4.6 RouteStop aggregate child

RouteStop, aynı müşteri teslimat adresine bağlı sıralı duraktır. `customer_id` ile `address_id` aynı müşteriye ait olmalıdır. Adres, müşteri adres master’ından gelir; route stop üzerinde yalnızca operasyonel zaman/status ve gelecekteki proof alanları bulunur.

```text
Pending → InProgress → Delivered / Partial / Failed / Skipped
```

Bu slice’ta yalnızca `Pending` durak oluşturma ve sıralama kullanılır. `InProgress` ve teslimat state’leri L5 package delivery slice’ında uygulanır.

## 5. Persistence tasarımı

### 5.1 Tablolar

| Tablo | Bu slice sorumluluğu | Önemli alanlar |
|---|---|---|
| `vehicle_types` | Araç sınıfı | `id`, `code`, `name`, `is_active` |
| `vehicle_capacities` | Effective kapasite profili | `vehicle_type_id`, effective dates, dimensions, weight, volume, policy snapshot |
| `vehicles` | Gerçek araç | `vehicle_type_id`, normalized plate, status, maintenance, row_version |
| `drivers` | Şoför kartı | `employee_id`, full name, phone, normalized license, expiry, status, row_version |
| `route_plans` | Shipment route version | `shipment_id`, vehicle, driver, status, version, times, row_version |
| `route_stops` | Customer address stop | route, sequence, customer, address, status, planned/actual times |
| `audit_logs` | Kritik master/state changes | status, assignment, lock, replan, override |
| `idempotency_records` | Command replay | existing shared store |

### 5.2 Gerekli schema düzeltmeleri

Canonical SQL taslağı route ve vehicle tablolarını tanımlamaktadır [5]. Uygulama migration’ında aşağıdaki alanlar/kurallar kesinleştirilmelidir:

| Konu | Tasarım kararı |
|---|---|
| `row_version` | `vehicles`, `drivers`, `route_plans` ve `route_stops` için `bigint NOT NULL DEFAULT 1`, EF concurrency token ve public ETag |
| Vehicle capacity duplicate alanları | Fiziksel/effective alanlar `vehicle_capacities` içine alınmalı; `vehicle_types` kimlik kaydına indirgenmeli |
| Effective capacity overlap | `(vehicle_type_id, effective_window)` için overlap engeli; en azından transaction lock + exclusion constraint |
| Route assignment time | `planned_start_at`, `planned_end_at` UTC; yarı açık interval `[start, end)` |
| Vehicle/driver overlap | Aktif route state’leri için vehicle ve driver bazında overlap constraint veya lock/re-read + typed conflict |
| Replan | `replanned_from_id` nullable self-FK, new `version`, `reason` ve audit |
| Current route projection | `vehicles.current_route_plan_id` varsa yalnızca projection; RoutePlan assignment source of truth |
| Stop order | `UNIQUE(route_plan_id, sequence_no)` + `sequence_no > 0` |
| Customer address | `route_stops.address_id` FK ve service-level customer ownership check |
| Delete behavior | Route/assignment history için `RESTRICT`; locked plans fiziksel silinmez |

### 5.3 Önerilen index’ler

| Index | Amaç |
|---|---|
| `vehicle_types(code)` unique | Master lookup |
| `vehicle_capacities(vehicle_type_id, effective_from)` | Effective profile lookup |
| `vehicles(plate_number)` unique | Duplicate plate prevention |
| `vehicles(status, maintenance_until)` | Available candidate query |
| `drivers(license_number)` unique veya aktif filtered unique | Ehliyet duplicate kontrolü |
| `route_plans(shipment_id, version)` unique | Route versioning |
| `route_plans(vehicle_id, planned_start_at, planned_end_at)` | Vehicle conflict query |
| `route_plans(driver_id, planned_start_at, planned_end_at)` | Driver conflict query |
| `route_stops(route_plan_id, sequence_no)` unique | Stop order |
| `route_stops(customer_id, status)` | Route/customer board |
| `idempotency_records(scope, key)` | Replay/mismatch |

PostgreSQL’te zaman aralığı overlap’ını database seviyesinde güçlendirmek için `tstzrange` + GiST exclusion constraint değerlendirilebilir. `btree_gist` extension kullanılmıyorsa minimum güvenlik; ilgili vehicle/driver row’larını deterministic sırada `FOR UPDATE` kilitlemek, aktif route’ları tekrar okumak ve overlap’i transaction içinde doğrulamaktır. Uygulama ve database kuralı birlikte kullanılır; yalnızca UI kontrolü kabul edilmez.

### 6.4 RoutePlan draft

```http
POST /api/v1/shipments/{shipmentId}/route-plans
```

**Permission:** `shipment.route-manage`
**Idempotency:** Zorunlu
**Başarı:** `201 Created`

```json
{
  "plannedStartAt": "2026-08-17T08:00:00Z",
  "plannedEndAt": "2026-08-17T16:00:00Z",
  "expectedShipmentRowVersion": 2
}
```

Shipment `Preparing` veya `Ready` olmalıdır. Endpoint draft route oluşturur; araç/şoför ve stop listesi henüz boş olabilir. Aynı shipment için aynı version tekrar oluşturulamaz.

### 6.5 Draft stop listesi

```http
POST /api/v1/route-plans/{routePlanId}/stops/replace
```

**Permission:** `shipment.route-manage`
**Idempotency:** Zorunlu
**If-Match:** RoutePlan ETag zorunlu
**Kural:** Yalnızca `Draft` plan düzenlenebilir.

```json
{
  "expectedRowVersion": 1,
  "stops": [
    {
      "sequenceNo": 1,
      "customerId": "22222222-2222-2222-2222-222222222222",
      "addressId": "33333333-3333-3333-3333-333333333333",
      "plannedArrivalAt": "2026-08-17T10:00:00Z"
    },
    {
      "sequenceNo": 2,
      "customerId": "44444444-4444-4444-4444-444444444444",
      "addressId": "55555555-5555-5555-5555-555555555555",
      "plannedArrivalAt": "2026-08-17T13:00:00Z"
    }
  ]
}
```

Server her `addressId` değerinin `customerId` ile eşleştiğini doğrular. `sequenceNo` duplicate veya `1..N` dışında ise `ROUTE_STOP_SEQUENCE_INVALID` döner. Stop replacement atomiktir; kısmi stop listesi bırakmaz.

### 6.6 Araç ve şoför ataması

```http
POST /api/v1/route-plans/{routePlanId}/assign-resources
```

**Permission:** `shipment.route-manage`
**Idempotency:** Zorunlu
**If-Match:** RoutePlan ETag zorunlu
**Başarı:** `200 OK`

Araç ve şoför aynı command’de atanır. Böylece araç atanıp şoför atanamayan yarım route assignment bırakılmaz.

```json
{
  "vehicleId": "66666666-6666-6666-6666-666666666666",
  "driverId": "77777777-7777-7777-7777-777777777777",
  "expectedRowVersion": 3
}
```

Transaction içinde vehicle ve driver kaynakları deterministik GUID sırasıyla kilitlenir; bakım, aktiflik, ehliyet expiry, route schedule overlap ve mevcut state yeniden okunur. Başarılı atamada RoutePlan üzerinde vehicle/driver FK’leri set edilir; araç state’i `Assigned` projection/command ile atomik güncellenir; shipment state’i değişmez.

### 6.7 Route planlama

```http
POST /api/v1/route-plans/{routePlanId}/plan
```

**Permission:** `shipment.route-manage`
**Idempotency:** Zorunlu
**If-Match:** RoutePlan ETag zorunlu
**Geçiş:** `Draft → Planned`

Guard’lar: shipment source valid, en az bir stop, sequence valid, time range valid, vehicle/driver assignment tamam, vehicle/driver conflict yok. Bu endpoint route’u kilitlemez; kullanıcı son kontrol için `Planned` durumda görür.

### 6.8 Route lock

```http
POST /api/v1/route-plans/{routePlanId}/lock
```

**Permission:** `shipment.route-lock`
**Idempotency:** Zorunlu
**If-Match:** RoutePlan ETag zorunlu
**Geçiş:** `Planned → Locked`

```json
{
  "confirmation": true,
  "expectedRowVersion": 5,
  "reason": "17 Ağustos sevkiyat rotası depo sorumlusu tarafından onaylandı."
}
```

Lock transaction’ı shipment, route plan, vehicle ve driver state’lerini tekrar okur. Tüm stop’lar valid, adres sahipliği doğru, zaman aralığı geçerli ve aktif schedule conflict yoksa plan lock edilir. Lock sonrası route stop/vehicle/driver/time doğrudan değiştirilemez; düzeltme `POST /route-plans/{id}/replan` ile yeni version ister.

### 6.9 Replan

```http
POST /api/v1/route-plans/{routePlanId}/replan
```

**Permission:** `shipment.route-manage` veya policy’ye göre `shipment.plan-replan`
**Idempotency:** Zorunlu
**If-Match:** Mevcut route ETag zorunlu
**Başarı:** `201 Created`

```json
{
  "reason": "Müşteri B teslimat penceresi değişti.",
  "plannedStartAt": "2026-08-17T09:00:00Z",
  "plannedEndAt": "2026-08-17T17:00:00Z",
  "copyStops": true,
  "copyResources": true
}
```

Eski locked plan değişmeden kalır. Yeni plan `version + 1`, `replannedFromId`, yeni row version ve audit ile oluşturulur. Yeni plan lock edilene kadar eski locked plan operasyonel referans olarak korunur.

## 8. Zaman çakışması ve concurrency sözleşmesi

### 8.1 Zaman aralığı

Route plan zamanı UTC ve yarı açık aralık olarak yorumlanır:

```text
[start, end)
```

Böylece bir rota `10:00`’da bitip sonraki rota `10:00`’da başlıyorsa aralıklar çakışmaz. `end <= start` geçersizdir. Zaman aralığı eksik draft plan oluşturulabilir; lock/plan aşamasında zorunlu hale gelir.

### 8.2 Assignment transaction sırası

```text
validation
→ authorization
→ idempotency lookup
→ transaction begin
→ RoutePlan row lock
→ Shipment row lock
→ Vehicle + Driver rows deterministic lock
→ fresh route/version read
→ maintenance/license/status checks
→ active route overlap check
→ assignment/state update
→ audit + outbox
→ SaveChanges
→ idempotency result
→ commit
```

Vehicle ve driver lock sırası GUID veya normalized numeric order ile sabitlenmelidir. İki kullanıcı aynı vehicle/driver kaynağını farklı route plan’lara atadığında yalnızca bir command commit eder; diğeri typed conflict alır.

### 8.3 ETag ve retry

Stale `If-Match` retry değildir; önce fresh GET, sonra kullanıcı onayı ile yeni command gerekir. PostgreSQL deadlock için yalnızca idempotent command’lerde sınırlı jitter retry uygulanabilir. `ROUTE_SCHEDULE_CONFLICT`, `DRIVER_LICENSE_EXPIRED` ve `VEHICLE_MAINTENANCE` kullanıcı düzeltmesi gerektiren non-retryable business conflict’tir.

## 11. Acceptance ve test matrisi

### 11.1 Domain unit

| Test | Beklenen |
|---|---|
| Vehicle available → assigned | Geçerli |
| Maintenance araç assignment | Reddedilir |
| OutOfService araç assignment | Reddedilir |
| Active driver license valid | Geçerli |
| Expired license | Reddedilir |
| Draft → Planned → Locked | Geçerli guard’larla geçer |
| Locked route stop mutation | Reddedilir |
| Duplicate stop sequence | Reddedilir |
| Customer/address mismatch | Reddedilir |
| End <= start | Reddedilir |
| Replan locked route | Yeni version üretir; eski değişmez |

### 11.2 Persistence/model

`vehicle_types`, `vehicle_capacities`, `vehicles`, `drivers`, `route_plans` ve `route_stops` mapping’leri; FK restrict, unique plate/license, status checks, effective profile checks, sequence unique, row version concurrency token, indexes ve route version self-FK ile doğrulanmalıdır.

### 11.3 PostgreSQL integration/concurrency

Aynı vehicle veya driver’ı aynı zaman aralığında iki route’a atayan iki ayrı database connection test edilmelidir. Beklenen sonuç bir commit ve bir typed schedule conflict’tir. Farklı zaman aralıkları `[start,end)` semantiğiyle birlikte kabul edilmelidir. İki kaynağın lock sırası deterministik olmalı; deadlock oluşursa command kontrollü biçimde rollback/retry politikasına uymalıdır.

Ayrıca şu integration senaryoları gereklidir:

- L2 `Ready` shipment için route draft oluşturma.
- Geçersiz veya bulunmayan shipment için route oluşturma reddi.
- Address ownership ihlali.
- Aynı shipment için duplicate route version.
- Route lock sonrası doğrudan edit reddi.
- Replan sonrası eski locked route’un değişmeden kalması.
- Vehicle status değişikliğinin audit ve ETag üretmesi.
- Capacity effective profile değişikliğinin eski route response’unu bozmaması.
- Route/vehicle/driver command’lerinin stock movement oluşturmaması.

### 11.4 API/security

Gerçek `/api/v1/auth/login` üzerinden full user, route-manage user, read-only user ve anonymous boundary test edilmelidir. Read-only kullanıcı `GET` yapabilir, ancak resource assignment/route lock/status update yapamaz. Başka shipment ID’si ile route detail ve başka vehicle/driver ID’si ile mutation denendiğinde IDOR/BOLA açığı oluşmamalıdır.

| Katman | Gate |
