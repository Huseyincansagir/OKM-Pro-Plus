# G6.2 L4-B — ShipmentPackage, LoadPlan Draft ve FFD Entegrasyonu

**Durum:** Kodlama öncesi teknik tasarım ve implementation gate

**Kapsam:** Bu doküman, committed L4-A Physical Logistics Master üzerine kurulacak L4-B bounded slice’ını tanımlar. Slice; issued delivery note’tan türemiş shipment kalemlerinin fiziksel `ShipmentPackage` kayıtlarına normalize edilmesini, route-stop sahipliğinin doğrulanmasını, draft `LoadPlan` oluşturulmasını, araç adaylarının açıklanabilir biçimde değerlendirilmesini ve deterministik First Fit Decreasing önerisi üretilmesini kapsar [1] [2].

**Kapsam dışı:** Gerçek araç rezervasyonu, yükleme barkodu, mobil yükleme, teslimat proof, GPS/traffic provider, optimal 3D bin-packing, aks güvenliği garantisi ve aynı araçta çoklu shipment optimizasyonu bu slice’a alınmaz. `LoadPlan.Locked` için gerekli approval/concurrency tasarımı belirtilir; implementation sırası içinde lock ayrı bir approval gate’i olarak tutulur.

> **Temel sınır:** Shipment ve stok miktarı source of truth olarak kalır. L4-B fiziksel dağıtım ve taşıma önerisi üretir; ikinci bir stok hareketi veya ticari miktar değişikliği üretemez.

## 1. Mevcut baseline ve L4-B boşluğu

Committed G6.2 baseline’ında `shipments`, `shipment_items`, `vehicle_capacities`, `vehicles`, `route_plans` ve `route_stops` uygulanmıştır. `ShipmentRecord` yalnızca issued delivery note kaynağını, müşteriyi, durumu ve row version’ı taşır; `ShipmentItemRecord` ise shipment item miktarını `quantity_base` ve packaging snapshot ile saklar. Route plan shipment’a bağlı version’lıdır; route stop kayıtlarında customer, address, sequence ve status bulunur [3].

L4-A tarafında ürün ve ambalaj fiziksel profilleri `effective_from/effective_to` aralığıyla, ölçüler `mm`, ağırlıklar `kg`, hacim ise `m3` olarak saklanmaktadır. L4-B’nin internal standardı mevcut L4-A source of truth ile aynı olmalıdır; bu nedenle önceki taslaklarda geçen `g` veya `mm3` alternatifleri bu implementation için kullanılmayacaktır. Dönüşümler yalnızca application hesaplama katmanında yapılır ve snapshot’a yazılır.

Mevcut baseline’da henüz şu kayıtlar yoktur:

| Eksik bounded yapı | L4-B rolü |
|---|---|
| `ShipmentPackage` | Shipment item’ın fiziksel ve planlama birimi |
| `LoadPlan` | Version’lı draft/proposal ve validation sonucu |
| `LoadUnit` | Palet, kafes, carton group veya loose fiziksel taşıma birimi |
| `LoadUnitItem` | Package/item’ın LoadUnit içindeki allocation’ı |
| `LoadUnitStopAllocation` | LoadUnit içindeki miktarın durak dağılımı |
| `VehicleFitEvaluation` | Aday araç, kullanım oranı ve rejection nedeni |
| `LoadPlanValidationResult` | Hard error, warning, info ve resolution |
| `LoadPlanManualChange` | Manuel değişiklik, gerekçe ve audit kanıtı |

## 2. Bounded alt-slice sırası

L4-B tek bir büyük transaction olarak yazılmamalıdır. Uygulama sırası şöyledir:

| Alt-slice | İçerik | Çıkış gate’i |
|---|---|---|
| L4-B1 | ShipmentPackage normalization ve route-stop ownership | Her package miktarı shipment ceiling içinde, stop sahipliği doğru |
| L4-B2 | LoadPlan Draft, LoadUnit ve allocation persistence | Draft plan server-side miktar tavanını koruyor |
| L4-B3 | VehicleFitEvaluation ve deterministic FFD suggestion | Aynı snapshot aynı sonucu üretiyor |
| L4-B4 | Validate, manual change, approval ve LockLoadPlan | Hard error yok, warning çözülmüş, approval ve ETag geçerli |

L4-B1 ve L4-B2 tamamlanmadan FFD engine gerçek shipment verisi üzerinde çalıştırılmamalıdır. L4-B3 `suggest` ve `evaluate` side-effect sınırını draft/evaluation kayıtlarıyla sınırlamalıdır. L4-B4 ayrı implementation slice olarak kalmalıdır.

## 3. Domain sınırları ve invariant’lar

### 3.1 ShipmentPackage

`ShipmentPackage`, shipment item’ın fiziksel planlama kaydıdır; ticari ürün kartı değildir. MVP’de bir kayıt, aynı packaging ve aynı fiziksel snapshot’a sahip homojen bir package batch’i temsil eder. Gerçek tekil barkodlu fiziksel paket takibi sonraki load-verification slice’ında `package_unit` ayrıştırmasıyla genişletilebilir.

Önerilen alanlar:

| Alan | Kural |
|---|---|
| `shipmentId` | Shipment’a ait olmalı |
| `shipmentItemId` | Shipment item’a ait olmalı; cross-shipment bağ yasak |
| `packagingId` | Shipment item packaging snapshot’ıyla uyumlu olmalı |
| `packageType` | `Case`, `Package`, `Pallet`, `Loose` gibi sınırlı enum |
| `packageCount` | Pozitif olmalı |
| `quantityBasePerPackage` | Pozitif olmalı |
| `quantityBase` | `packageCount × quantityBasePerPackage` ile server hesaplanmalı |
| `enteredQuantity` | UI audit’i için saklanabilir; doğruluk kaynağı değildir |
| `packagingSnapshot` | İsim, level, conversion ve effective profile snapshot’ı |
| `physicalSnapshot` | Ölçü, net/tare/gross, orientation ve compatibility snapshot’ı |
| `routeStopId` | Route plan aynı shipment’a aitse dolu olabilir |
| `splitAllowed` | Package’ın LoadUnit allocation’da bölünüp bölünemeyeceği |
| `status` | `Available`, `Allocated`, `Loaded`, `Cancelled` |
| `rowVersion` | ETag/concurrency |

L4-B1 için package quantity server-side hesaplanır. `Σ shipment_packages.quantity_base` ilgili shipment item quantity’sini aşamaz. `splitAllowed=false` package tek bir aktif LoadUnit allocation’ında bulunur. Package’ı iki farklı route stop’a dağıtmak yasaktır; farklı stop’lara bölme shipment item düzeyinde yeni package satırlarıyla yapılmalıdır.

### 3.2 LoadPlan

`LoadPlan`, shipment ve route plan version’ına bağlı immutable/version’lı plan aggregate’ıdır. Plan ticari miktarı veya stock movement’ı değiştirmez.

State akışı:

```text
Draft → Proposed → Validating → Valid
Draft/Proposed/Valid/NeedsReview → Superseded (new version)
Valid → NeedsReview
Valid → Locked (approval gate)
Locked → Superseded (only through replan)
```

`FeasibilityStatus` ayrı sonuç alanıdır:

```text
Infeasible
FeasibleWithWarnings
Feasible
```

Aşağıdaki invariant’lar zorunludur:

1. Aynı `(shipment_id, version)` ikinci kez oluşturulamaz.
2. Draft oluşturulurken `shipment_id`, `route_plan_id` ve `route_plan_version` aynı shipment/route zincirine ait olmalıdır.
3. `LoadUnitItem` ve `LoadUnitStopAllocation` toplamları shipment package/item ceiling’ini aşamaz.
4. `Locked` plan için `vehicle_id`, `vehicle_capacity_id`, route version, input snapshot hash, capacity snapshot ve approval bilgisi dolu olmalıdır.
5. Hard validation error varken plan `Locked` olamaz.
6. Warning’ler çözülmemişse `LOAD_PLAN_APPROVAL_REQUIRED` döner; yalnızca yetkili override ile warning kapanabilir.
7. Locked plan doğrudan mutate edilemez; yeni version ve `replanned_from_id` oluşturulur.
8. `suggest` veya `evaluate` gerçek araç status’ünü `Assigned` yapmaz ve departure/stock side-effect üretmez.

### 3.3 LoadUnit ve allocations

`LoadUnit`, fiziksel taşıma birimidir. `unitType` `Pallet`, `Cage`, `CartonGroup` veya `Loose` değerlerinden biri olabilir. `isMixed=true` farklı shipment item’ların aynı unit içinde bulunmasına izin verir; uyumsuzluk ve stop access hard/soft policy ile yeniden değerlendirilir.

`LoadUnitItem` package veya shipment item allocation’ını taşır. Aynı shipment item’ın farklı unit’lere bölünmesi yalnızca `splitAllowed=true` ise mümkündür. `LoadUnitStopAllocation`, unit item miktarını route stop’a bağlar. Her stop allocation için şu ownership zinciri doğrulanır:

```text
LoadPlan → RoutePlan → RouteStop
LoadUnitItem → ShipmentPackage → ShipmentItem → Shipment
```

Foreign key’ler tek başına bu zinciri garanti etmez. Command service transaction içinde bütün parent zincirlerini tekrar okuyup doğrulamalıdır.

## 4. L4-B PostgreSQL şema tasarımı

### 4.1 `shipment_packages`

```sql
create table shipment_packages (
    id uuid primary key,
    shipment_id uuid not null references shipments(id) on delete restrict,
    shipment_item_id uuid not null references shipment_items(id) on delete restrict,
    packaging_id uuid null references product_packagings(id) on delete restrict,
    route_stop_id uuid null references route_stops(id) on delete restrict,
    package_type varchar(30) not null,
    package_count numeric(18,6) not null,
    quantity_base_per_package numeric(18,6) not null,
    quantity_base numeric(18,6) not null,
    entered_quantity numeric(18,6) null,
    package_code varchar(120) null,
    packaging_snapshot jsonb not null,
    physical_snapshot jsonb not null,
    split_allowed boolean not null default false,
    status varchar(30) not null default 'Available',
    created_at timestamptz not null,
    updated_at timestamptz not null,
    row_version bigint not null default 1,
    constraint ck_shipment_packages_type
        check (package_type in ('Case','Package','Pallet','Loose')),
    constraint ck_shipment_packages_status
        check (status in ('Available','Allocated','Loaded','Cancelled')),
    constraint ck_shipment_packages_quantity_positive
        check (package_count > 0 and quantity_base_per_package > 0 and quantity_base > 0),
    constraint ck_shipment_packages_quantity_formula
        check (quantity_base = package_count * quantity_base_per_package)
);

create index ix_shipment_packages_shipment_status
    on shipment_packages (shipment_id, status);
create index ix_shipment_packages_item
    on shipment_packages (shipment_item_id);
create index ix_shipment_packages_stop
    on shipment_packages (route_stop_id);
create unique index ux_shipment_packages_active_code
    on shipment_packages (package_code)
    where package_code is not null and status <> 'Cancelled';
```

`quantity_base` database CHECK ile formül olarak tutulabilir; yüksek hassasiyetli decimal çarpımında rounding policy ayrıca application’da belirlenmelidir. Package count’ın fractional olmasına izin verilmeyecek packaging seviyelerinde service `package_count` değerini tam sayı olarak doğrulamalıdır.

## 5. Source-of-truth ve snapshot kuralları

L4-B hesaplamasında client’tan gelen utilization, gross weight, volume veya feasibility alanları doğruluk kaynağı değildir. Server şu sırayla okur ve hesaplar:

```text
ShipmentItem.quantity_base
→ ShipmentPackage conversion ve packaging snapshot
→ ProductPhysicalProfile / PackagingPhysicalProfile as-of seçimi
→ PlanningItem normalization
→ LoadUnit allocation
→ VehicleCapacity effective snapshot
→ validation ve FFD
```

`ShipmentPackage.packaging_snapshot` içinde en az packaging id, level, units-per-package, effective date ve quantity conversion saklanmalıdır. `physical_snapshot` içinde ölçüler, net/tare/gross, volume, compatibility, orientation, stackability ve kaynak profile id/effective date saklanmalıdır. Böylece L4-A master profile ileride değişse bile eski package ve locked plan yeniden yorumlanmaz.

`LoadPlan.input_snapshot_hash` canonical JSON input’un SHA-256 hash’i olmalıdır. Hash içine shipment item miktarları, package snapshot’ları, route plan id/version ve stop sequence, vehicle/capacity snapshot, algorithm version ve parameter set dahil edilmelidir. Database insertion order veya random UUID sort key’e dahil edilmemelidir.

## 6. Deterministic FFD entegrasyonu

### 6.1 Normalization

`PlanningItem` server-side oluşturulur. Her item için şu alanlar hesaplanır:

```text
shipmentPackageId
shipmentItemId
productId
packagingId
quantityBase
packageCount
netWeightKg
packagingTareKg
grossWeightKg
volumeM3
lengthMm / widthMm / heightMm
compatibilityGroup
incompatibleGroups
isFragile
keepUpright
allowedOrientations
splitAllowed
routeStopSequence
stableSortKey
```

Stable sort key şu sırayı kullanmalıdır:

```text
compatibilityGroup ASC
keepUpright DESC
isFragile DESC
grossWeightKg DESC
volumeM3 DESC
floorFootprint DESC
routeStopSequence ASC
shipmentItemId ASC
packagingId ASC
shipmentPackageId ASC
```

UUID veya insertion order tek başına tie-breaker olarak kullanılmaz. Aynı `input_snapshot_hash`, `algorithm_version` ve `parameter_set` aynı sırayı üretmelidir.

### 6.2 FFD akışı

```text
1. Shipment, route, stops, packages ve effective physical profiles’i oku.
2. Ownership ve quantity ceiling doğrula.
3. Eksik fiziksel profile sahip item’ları PHYSICAL_PROFILE_MISSING olarak ayır.
4. Valid PlanningItem listesini stable sort key ile sırala.
5. Mevcut LoadUnit’leri unitCode ASC ile sırala.
6. Her item için unit adaylarını hard constraint sırasıyla test et.
7. Hard constraint geçen adaylar için penalty hesapla.
8. En düşük penalty’li adayı seç; eşitlikte daha az unit, daha iyi stop access, daha az mixed customer ve unitCode ASC kullan.
9. Uygun aday yoksa yeni LoadUnit aç.
10. Unsplittable package sığmıyorsa Infeasible validation üret.
11. Split-enabled item için kalan miktarı kontrollü şekilde sonraki unit’e taşı.
12. Stop allocation toplamlarını yeniden hesapla.
13. Her araç için VehicleFitEvaluation snapshot’ı üret.
14. ValidationSummary ve FeasibilityStatus üret.
15. Draft/Proposed LoadPlan ve allocation’ları transaction içinde kaydet.
```

Hard constraint sırası:

| Sıra | Kontrol | Kod |
|---:|---|---|
| 1 | Quantity ceiling | `QUANTITY_EXCEEDED` |
| 2 | Physical profile | `PHYSICAL_PROFILE_MISSING` |
| 3 | Unit gross weight | `LOAD_UNIT_WEIGHT_EXCEEDED` |
| 4 | Unit volume | `LOAD_UNIT_VOLUME_EXCEEDED` |
| 5 | Dimensions/door | `LOAD_UNIT_DIMENSION_MISMATCH`, `DOOR_OPENING_MISMATCH` |
| 6 | Compatibility | `COMPATIBILITY_BLOCK` |
| 7 | Stacking/crush | `STACKING_NOT_ALLOWED` |
| 8 | Orientation | `ORIENTATION_NOT_ALLOWED` |
| 9 | Package/stop ownership | `PACKAGE_STOP_MISMATCH` |
| 10 | Stop access | `STOP_ACCESS_BLOCK` veya policy’ye göre warning |

FFD optimal 3D packing iddiasında bulunmaz. Response ve audit içinde algorithm name/version, parameter set, input hash, item ordering ve rejection reason bulunmalıdır.

## 8. Transaction ve concurrency

Package create transaction sırası:

```text
Shipment FOR UPDATE
→ ShipmentItem FOR UPDATE
→ RoutePlan/RouteStop ownership read
→ active package rows FOR UPDATE
→ server quantity ceiling
→ profile snapshot
→ package insert + shipment row version + audit/idempotency
→ commit
```

Suggest/evaluate snapshot üretiminde side-effect minimum tutulabilir; aynı snapshot için idempotent evaluation kayıtları yazılır. Final lock transaction sırası şöyledir:

```text
LoadPlan FOR UPDATE
→ Shipment FOR UPDATE
→ RoutePlan FOR UPDATE
→ RouteStops deterministic sequence
→ ShipmentPackages deterministic id ASC
→ LoadUnits deterministic unit_code ASC
→ selected Vehicle FOR UPDATE
→ VehicleCapacity effective profile FOR UPDATE/consistent read
→ route overlap ve capacity revalidation
→ hard/warning/approval guard
→ Locked + approval + audit/idempotency
→ commit
```

`SKIP LOCKED` final lock’ta kullanılmaz; kilitli kaynağı görünmez kılar. Stale ETag `RESOURCE_VERSION_CONFLICT`, package başka planla aktif bağlıysa `PACKAGE_ALREADY_ASSIGNED`, değişmiş capacity snapshot `CAPACITY_SNAPSHOT_STALE`, araç route overlap’ı `VEHICLE_SCHEDULE_CONFLICT`, hard validation `LOAD_PLAN_INFEASIBLE`, çözülmemiş warning `LOAD_PLAN_APPROVAL_REQUIRED` ile eşlenir.

Aynı `Idempotency-Key` aynı payload ile tekrarlandığında ilk response replay edilir. Payload hash farklıysa `IDEMPOTENCY_PAYLOAD_MISMATCH` dönmeli ve ikinci side-effect oluşmamalıdır.

## 9. Migration sırası

```text
M1 shipment_packages + shipment item/route ownership indexes
M2 load_plans + version/status/feasibility/snapshot fields
M3 load_units + load_unit_items
M4 load_unit_stop_allocations
M5 vehicle_fit_evaluations
M6 load_plan_validation_results
M7 load_plan_manual_changes
M8 partial/unique indexes, CHECK constraints and row_version mappings
M9 backfill/verification and NOT NULL hardening
```

M1’de mevcut shipment item quantity’leri package olmadan bırakılabilir; ancak L4-B4 lock öncesi her shipment item’ın package coverage’ı zorunlu hale getirilmelidir. Backfill sırasında package conversion için delivery note/shipment packaging snapshot source of truth kabul edilmelidir.
